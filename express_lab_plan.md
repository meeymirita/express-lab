> Статус: **план и ТЗ утверждены владельцем (11–12.10.2026)**: домен «пользователи + загрузка + короткие ссылки», размер «средний и чуть больше», локально на Mac. **Методички и кода нет, ничего не проверялось.** Этот файл — единственный документ лабы: паспорт, сессии, ТЗ проекта.

## Зачем лаба

В репозитории есть `nestjs`, `graphql`, `typescript`, но нет введения в сам **Node.js** и **Express**. NestJS-лаба просит «основы JS и Node», а объясняет только Nest. Nest работает поверх Express, и без Express непонятно, чем Guards / Pipes / Interceptors отличаются от обычных middleware.

Лаба закрывает пробел: **Node → Express → то, что потом скрывает Nest**. Идёт перед `typescript` и `nestjs`.

# ТЗ: ShareBox

### 1. Цель продукта

Пользователь регистрируется, загружает файлы и делится ими по короткой ссылке. Получателю аккаунт не нужен, если ссылка публичная.

Учебная цель: пройти путь от «голого» `node:http` до готового, защищённого и протестированного Express-сервиса и понять, что именно потом автоматизирует NestJS.

### 2. Роли

| Роль | Кто | Что может |
|---|---|---|
| Аноним | кто угодно | открыть публичную ссылку, скачать файл (если ссылка позволяет), регистрация, вход |
| Пользователь | вошедший | загружать файлы, видеть и удалять **свои**, создавать и отзывать ссылки на свои файлы, смотреть статистику |
| Получатель | аноним или пользователь по ссылке | скачать файл по ссылке, если ссылка действует |
| Админ | пользователь с `role = admin` (создаётся скриптом `npm run create-admin`, не через регистрацию) | видеть все файлы, удалять любые, запускать чистку |

### 3. Сущности

**User** — `id`, `email` (уникальный), `passwordHash` (argon2), `role` (`user`/`admin`), `createdAt`.

**RefreshToken** — `id`, `userId`, `tokenHash`, `expiresAt`, `revokedAt`, `replacedBy`.

**File** — `id`, `ownerId`, `originalName`, `storedName` (случайное имя на диске), `mimeType`, `size`, `sha256`, `createdAt`, `deletedAt`.

**Share** — `id`, `fileId`, `code` (короткий, уникальный), `expiresAt` (может быть пустым), `maxDownloads` (может быть пустым), `downloads` (счётчик), `passwordHash` (может быть пустым), `revokedAt`, `createdAt`.

**DownloadLog** — `id`, `shareId`, `at`, `ip`, `userAgent`, `status` (`ok`/`expired`/`limit`/`bad_password`).

### 4. API

Все ответы JSON, кроме скачивания. Ошибки — единый формат `{ "error": { "code": "...", "message": "..." } }`.

#### Служебные
| Метод | Путь | Описание |
|---|---|---|
| GET | `/health` | сервер жив (200) |
| GET | `/ready` | готов принимать запросы: БД доступна (200/503) |

#### Аутентификация
| Метод | Путь | Описание |
|---|---|---|
| POST | `/auth/register` | `{ email, password }` → 201, без возврата хэша |
| POST | `/auth/login` | → `{ accessToken, refreshToken }` |
| POST | `/auth/refresh` | ротация refresh-токена; повторное использование старого — отзыв всей цепочки |
| POST | `/auth/logout` | отзыв refresh-токена |
| GET | `/me` | текущий пользователь |

#### Файлы (нужен вход)
| Метод | Путь | Описание |
|---|---|---|
| POST | `/files` | `multipart/form-data`, поле `file` → 201 + метаданные |
| GET | `/files` | свои файлы (пагинация `?page=&limit=`) |
| GET | `/files/:id` | метаданные своего файла |
| GET | `/files/:id/download` | скачать свой файл потоком |
| DELETE | `/files/:id` | удалить (запись и файл на диске) → 204 |

#### Ссылки
| Метод | Путь | Описание |
|---|---|---|
| POST | `/files/:id/shares` | создать ссылку: `{ expiresIn?, maxDownloads?, password? }` → 201 + `code` |
| GET | `/files/:id/shares` | ссылки на свой файл |
| DELETE | `/shares/:id` | отозвать → 204 |
| GET | `/shares/:id/stats` | счётчик и журнал скачиваний |
| GET | `/s/:code` | **публичный**: HTML-страница скачивания (имя, размер, форма пароля, кнопка «Скачать», готовые команды для консоли); с `Accept: application/json` — те же данные JSON |
| GET | `/s/:code/file` | **публичный**: сам файл потоком; пароль — заголовком `X-Share-Password` или `?password=`; поддерживает `Range` и докачку |
| POST | `/s/:code/download` | **публичный**: то же, пароль в теле `{ password }` (для формы на странице) |

#### Админ
| Метод | Путь | Описание |
|---|---|---|
| GET | `/admin/files` | все файлы всех пользователей |
| DELETE | `/admin/files/:id` | удалить любой файл |
| GET | `/admin/users` | список пользователей |
| POST | `/admin/cleanup` | запустить чистку вручную |

Код ответа публичной ссылки: 200 — ок; 401 — нужен/неверен пароль; 404 — такого кода нет; 410 — ссылка просрочена, отозвана или лимит исчерпан; 429 — слишком часто.

### 5. Правила и ограничения

**Файлы**
- максимальный размер — **200 МБ** (настраивается через `.env`); файл пишется на диск потоком, в память целиком не читается; лимит проверяется и по `Content-Length`, и по факту (прерывание при превышении), ответ 413;
- имя на диске — случайное (`crypto.randomUUID()`), оригинальное имя хранится только в БД и отдаётся в `Content-Disposition` после очистки;
- тип проверяется по содержимому (первые байты), а не только по заголовку клиента; список разрешённых типов в конфиге;
- запись только внутрь каталога хранилища, никаких `..` и абсолютных путей;
- на каждый файл считается `sha256`.

**Ссылки**
- код — 8 символов (`a-z0-9`), генерируется криптографически стойким генератором, при коллизии повтор;
- срок жизни по умолчанию 7 суток, максимум 30; `maxDownloads` от 1 до 1000;
- пароль ссылки хранится только хэшем;
- счётчик скачиваний увеличивается атомарно (в одной транзакции с проверкой лимита), чтобы два параллельных запроса не обошли лимит.

**Безопасность**
- пароли — `argon2`; access-токен — 15 минут; refresh — 7 суток с ротацией;
- владение: чужой файл возвращает 404 (а не 403), чтобы не раскрывать существование;
- rate limit: вход — 10/мин с IP; публичные `/s/*` — 30/мин с IP;
- заголовки `helmet`, CORS из списка разрешённых источников;
- в логи не попадают пароли, токены, коды ссылок целиком.

**Эксплуатация**
- конфиг только из `.env`, с проверкой при старте (приложение не стартует с неверным конфигом);
- логи `pino` в JSON, у запроса есть `requestId`;
- graceful shutdown: на `SIGTERM` перестать принимать новые запросы, дождаться текущих, закрыть пул БД;
- фоновая чистка (раз в час): просроченные ссылки помечаются, файлы без активных ссылок и старше N дней — по настройке удаляются.

### 5а. Страница скачивания и скачивание из консоли

**HTML-страница** `/s/:code` — одна простая страница без фреймворка (HTML + немного JS, отдаётся самим Express): имя и размер файла, срок жизни, остаток скачиваний, поле пароля (если он нужен), кнопка «Скачать», блок «Скачать из консоли» с готовыми командами, подставленными под эту ссылку.

**Обязательная часть лабы — подробное объяснение, как скачивать файл через консоль** (студент этого не умеет, объяснять с нуля). Отдельный раздел методички и шпаргалка, на примере ссылки ShareBox:
- что такое консоль и зачем скачивать из неё (серверы без браузера, скрипты, большие файлы);
- `curl`: что значит каждый флаг. `-O`, `-o имя`, `-L`, `-J`, `-C -` (докачка), `-H` (заголовок с паролем), `--progress-bar`, `-I` (только заголовки), `-v` (разговор клиента с сервером); как прочитать вывод построчно;
- `wget`: `-O`, `-c` (докачка), `--header`;
- макос/Linux и Windows (PowerShell `Invoke-WebRequest`, `curl.exe`); где файл окажется и как проверить, что скачался целиком (`ls -l`, `shasum -a 256` против `sha256` из метаданных);
- пароль: заголовок вместо `?password=` (почему так безопаснее — не оседает в истории браузера и логах);
- как обрывается и докачивается загрузка 200 МБ (`Range`, `Content-Range`, 206): студент сам обрывает `Ctrl+C` и докачивает;
- типичные ошибки с точным текстом: 401, 404, 410, 429, `curl: (18) transfer closed`, «Permission denied» при записи.

### 8. Критерии приёмки (итог лабы)

1. Регистрация, вход, `/me`, ротация refresh работают; повтор старого refresh отзывает цепочку.
2. Загрузка файла 150 МБ проходит, 250 МБ — отклоняется (413) без раздувания памяти; файл с поддельным расширением отклоняется.
3. Чужой файл по `id` — 404.
4. Ссылка с `maxDownloads=2`: третье скачивание — 410. Два одновременных запроса на последнее скачивание — выигрывает один.
5. Просроченная ссылка — 410, несуществующая — 404, неверный пароль — 401.
6. Скачивание большого файла (200 МБ) не раздувает память процесса (потоком), `Range` работает.
7. 11-й вход за минуту — 429.
8. `SIGTERM` во время скачивания не обрывает его, процесс завершается чисто.
9. `npm test` зелёный; `docker compose up` поднимает весь стенд; через Caddy всё доступно на одном порту.
10. Страница `/s/:code` открывается в браузере, скачивание с паролем и без работает; студент скачал файл через `curl` и `wget`, оборвал и докачал, сверил sha256.
11. Админ видит и удаляет чужие файлы, обычный пользователь получает 403 на `/admin/*`.
12. Финальная таблица «Express → NestJS» заполнена своими словами.

### Часть I. Node.js с нуля (новый раздел перед текущими, ≈ 8 сессий)

Пререквизит — **пройденный `js-lab`**. Часть I — ровно то, что языковая лаба сознательно не даёт: сеть, протокол HTTP и рантайм Node без браузера и без фреймворка. Темы объединены по смыслу, а не растянуты до круглого числа — где один рабочий блок (например, разбор протокола и свой сервер поверх него), там одна сессия, без искусственного дробления; идеи вроде регулярных выражений или HTTP как отдельной дисциплины включены не отдельными сессиями, а внутри той практики, где они реально нужны.

| № (черновой) | Сессия | Содержание |
|---|---|---|
| 1 | Node-рантайм и npm | `package.json`, npm-скрипты, `.env`; CJS `require` vs ESM `import` именно в Node (резолюция модулей, `"type": "module"`) — отличие от браузерного ESM из `js-lab`; структура CLI- и сервер-проекта |
| 2 | Файлы, Buffer, Streams | `node:fs`/`fs/promises`, `node:path`; Buffer и бинарные данные; Readable/Writable/pipe, backpressure; потоковое копирование и хеширование большого файла без загрузки его в память |
| 3 | Протокол HTTP и свой сервер | сам протокол руками (методы и статусы, заголовки, cookies, формы и `multipart/form-data`, chunked-передача, `curl` построчно, HTTPS и коротко HTTP/2-3) сразу применяется в собственном `node:http`-сервере: роутинг и разбор query/path без фреймворка (регулярки — как рабочий инструмент парсинга здесь, а не отдельная теоретическая тема), `node:crypto` |
| 4 | Процессы и параллелизм | `child_process`, `worker_threads`, `cluster` — разгрузка event loop на практике (например, вынести CPU-тяжёлую задачу из сессии 2–3 в отдельный поток) |
| 5 | Архитектура серверного кода | слои (routes/controllers/services в зачаточном виде на голом Node), DI руками, свои классы ошибок, валидация на границе — тот же слой, что потом без переписывания переедет в Express |
| 6 | Тестирование и отладка | `node:test`, **моки и стабы** (не ходить в реальную сеть/на диск в тестах — ключевое умение для финального проекта), профилирование, утечки памяти, необработанные исключения |
| 7 | Эксплуатационная граница | конфигурация и секреты, graceful shutdown, базовый прод-чеклист — этот же чек-лист расширяется в Части II |
| 8 | Финальный проект (см. ниже) | — |

Async/await, промисы, DOM, `fetch` используются по ходу, но не объясняются заново — в методичке ссылка на конкретный раздел `js-lab` вместо повтора. REST-семантику и HTTP API как дисциплину проектирования (коды, идемпотентность, OpenAPI) сюда не включаем отдельной сессией — это сильнее работает в Части II, на реальном API ShareBox, а не абстрактно до него.

**Финальный проект части I — «Загрузчик страниц» (CLI), без Express, без БД.** Не домен ShareBox намеренно: финалу части I важнее разнообразие практики, чем сюжетная связь с Express-частью. По URL скачивает HTML-страницу, находит ссылки на локальные ресурсы (картинки, CSS, JS), скачивает их и переписывает пути в HTML на локальные (здесь нужны регулярки из сессии 3), складывает всё в папку по имени страницы. Требования: обработка сетевых и файловых ошибок с понятными кодами выхода, тесты на моках/стабах (без реальной сети и диска), CLI-интерфейс, публикация как исполняемый бинарник (`bin` в `package.json`). Это ровно то умение — голый HTTP-клиент, парсинг и потоковая запись, процессный CLI — которого нет ни в `js-lab` (там только браузер), ни в ShareBox (там Node — HTTP-сервер, а не клиент).

### Часть II. Express — продолжение в той же работе (текущие 11 сессий → ≈ 13)

Текущие сессии 3–11 (роутинг, middleware, ошибки/структура, PostgreSQL, Prisma, аутентификация, файлы, ссылки, админ/надёжность, тесты/Docker/финал) остаются почти как есть. Добавляются темы, которых в текущем ТЗ ShareBox сейчас нет или они есть только implicit:

| Новая сессия | Куда | Зачем |
|---|---|---|
| REST-проектирование: версии API, идемпотентность, единый контракт ошибок, OpenAPI-описание | перед текущей сессией 4 («Ошибки, валидация, структура») | сейчас идемпотентность в ТЗ — только для счётчика скачиваний (раздел «Ссылки»); стоит сделать общей дисциплиной и дать OpenAPI ShareBox как артефакт |
| Конкурентные данные: N+1, оптимистичная блокировка, несколько операций в одной транзакции | вливается в текущую сессию 7 (PostgreSQL/Prisma), не отдельной сессией | ShareBox это уже частично требует (атомарный счётчик скачиваний, п. 4 критериев приёмки) — не нужна отдельная сессия, достаточно сделать явной темой внутри существующей |
| Наблюдаемость: request/correlation ID, простые метрики времени ответа и ошибок | вливается в текущую сессию 10 («Админ и надёжность»), не отдельной сессией | `pino` и graceful shutdown там уже есть — не хватает только ID запроса и пары счётчиков, не тянет на отдельную сессию |

Итого к текущим 11 добавляется фактически **одна** новая сессия (REST/OpenAPI), остальное — усиление существующих тем без раздувания числа сессий.

### Финальный проект части II (объёмнее первого)

Расширить ShareBox до командного пространства: рабочие пространства/команды, роли `owner`/`admin`/`member` на уровне команды (отдельно от нынешних `user`/`admin` ShareBox), общие папки со ссылками для участников, пакетный импорт файлов через фоновую очередь (своя, без Redis — см. выше), журнал изменений, webhook по факту скачивания, OpenAPI-документация всего API, деплой через Caddy с несколькими инстансами Express (stateless, без сессий в памяти процесса).

### Открытые вопросы владельцу

1. **Объём.** Части I + II вместе — 19 сессий, ~76 ч (для сравнения: Docker-лаба переписана в 12 сессий / ~44 ч и уже считается «большой лабой» в `plan/`). Больше любой существующей лабы репозитория — подтвердить, что это ок.
2. **Один подмодуль или два.** Проще всего — всё остаётся в текущей папке/репозитории `express` (один `express.html`), части I и II — сессии 1–8 и 9–19 внутри; переименование (например, в `node-express-lab`) не обязательно, но можно обсудить.
3. **Порядок относительно других лаб.** Сейчас `express` идёт перед `typescript`/`nestjs`, теперь ещё и после `js`. Решить, встраивать ли такой объём в очередь больших лаб (`fixes/common/_standard-lab.md`: Bash → Docker → Traefik → Kubernetes → Ansible) или держать отдельно, как сейчас.
