# Сессия 8 · Финал части I: Загрузчик страниц

## 8.1 Задание: CLI-загрузчик страниц | short: Итоговое задание части I | est: ~4 ч
### intro
**Слова шага:** *техническое задание (ТЗ)*, *приёмка*, *самопроверка*.

Новой теории в этой сессии нет: ты сама пишешь утилиту по описанию, используя всё из сессий 1–7 — голый Node, без Express и без базы данных. Готового решения здесь нет, и так задумано: опирайся на свой код из прошлых сессий (`fs/promises`, `node:path`, потоки, `worker_threads`, слои/ошибки/валидация, тесты на моках, graceful shutdown) и на справочные разделы методички.

**Задача.** Консольная утилита `page-loader`: по URL скачивает HTML-страницу, находит на ней локальные ресурсы (картинки `<img>`, таблицы стилей `<link rel="stylesheet">`, скрипты `<script src>` — только те, что с того же домена, что и сама страница), скачивает каждый ресурс, сохраняет рядом и переписывает пути в HTML на локальные.

**Запуск:**
```text
node bin/page-loader.mjs https://example.com --output ./out
```

**1. Имена файлов.** Страница `https://example.com/blog/post` сохраняется как `example-com-blog-post.html` (точки, слэши и небуквенно-цифровые символы в адресе — на дефисы), ресурсы — в папку `example-com-blog-post_files/` рядом, по тому же принципу именования из полного URL ресурса (включая расширение: `.png`, `.css`, `.js` — по содержимому ответа/заголовку `Content-Type`, не только по URL).

**2. Сеть.** Используй глобальный `fetch` (встроен в Node 24, без библиотек). Для страницы и для каждого ресурса — ошибки сети (таймаут, DNS, не-2xx статус) оборачиваются в свои классы ошибок (сессия 5.2: `status`, `cause` — исходная ошибка), а не всплывают как сырые исключения `fetch`.

**3. Параллельность и потоки.** Ресурсы страницы скачиваются **параллельно**, но не более `--limit` одновременно (по умолчанию 4) — пул, который сам решает, когда начинать следующий. Запись каждого ресурса на диск — **потоком** (сессия 2.4/2.5): `fetch` отдаёт `response.body` как `ReadableStream`, его нужно соединить с `fs`-потоком записи, не читая весь ресурс в память разом (особенно важно для крупных файлов).

**4. Парсинг и перезапись HTML.** Для поиска и правки тегов разреши себе библиотеку для разбора HTML (например, `cheerio` — `npm install cheerio`): писать свой парсер HTML регулярками — классическая и хорошо известная ошибка (HTML — не регулярный язык), это не тот навык, который здесь проверяется. А вот сопоставление URL (свой домен или чужой, абсолютный или относительный путь) делай сама, через `node:url`.

**5. Устойчивость.** Если один ресурс не скачался (например, 404), остальная загрузка **не должна** прерываться: страница сохраняется с тем, что получилось, а ресурс, который не скачался, перечисляется отдельным предупреждением в консоли со своей причиной, ссылка на него в HTML остаётся как была (внешняя, не переписанная).

**6. CLI и коды выхода.** Аргументы: обязательный URL, `--output`/`-o` (по умолчанию текущая папка), `--limit` (см. п. 3). Коды выхода: `0` — всё скачалось без ошибок; `1` — страницу вообще не удалось получить (ошибка сети на главном запросе); `2` — ошибка файловой системы (например, нет прав на запись в `--output`); частично неудавшиеся ресурсы (п. 5) — это не ошибка всей утилиты, код выхода всё равно `0`, но предупреждения напечатаны. Файл утилиты — с shebang (`#!/usr/bin/env node`) и полем `bin` в `package.json`, чтобы запускаться без явного `node` через `npx` или после `npm link`.

**7. Тесты.** Минимум четыре теста на `node:test`, **без обращения к реальной сети и реальному диску** (сессия 6.2: моки/стабы — подмени `fetch` на мок, файловую запись — на фиктивную функцию, принятую аргументом, как в `notifyFileCreated`). Например: имя файла страницы формируется верно из URL; ресурс с другого домена не скачивается и путь не переписывается; при ошибке одного ресурса остальные всё равно сохраняются; пул не запускает больше `--limit` скачиваний одновременно.

**Чего не требуется:** картинок с `srcset`, инлайновых стилей с `url(...)` внутри CSS, рекурсивного обхода ссылок на другие страницы (это не краулер, а загрузчик одной страницы), графического интерфейса.

**Порядок работы (подсказка, не решение):** сначала скачать и сохранить саму страницу без изменений; затем найти ресурсы и скачать их последовательно (без пула и без потоковой записи) — «счастливый путь»; затем переписать пути в HTML; затем параллельность с лимитом; затем устойчивость к ошибкам одного ресурса; затем CLI-обвязка и коды выхода; в конце — тесты.

### why
Здесь соединяется почти всё из части I: `fetch` и обработка сетевых ошибок (сессия 3), потоковая запись на диск (сессия 2), пул с ограничением параллельности (та же идея, что `worker_threads` в сессии 4, но для сетевых задач, а не вычислений), свои классы ошибок и валидация аргументов (сессия 5), тесты на моках без реальной сети (сессия 6), понятные коды выхода (сессия 7). Если на каком-то пункте застряла — это и есть тема, к которой стоит вернуться.

### quiz
- Проверь себя: выполнено ли задание?
- Имя сохранённой страницы и файлов ресурсов формируется по описанному правилу, включая небуквенно-цифровые символы в адресе.
- Ресурсы скачиваются не более чем `--limit` одновременно (проверено тестом, а не «на глаз»).
- Запись каждого ресурса на диск — потоком, а не через чтение всего ответа в память.
- Ресурс с чужого домена не скачивается, и его путь в HTML не переписывается.
- Если один ресурс не скачался, остальная загрузка не прерывается, причина видна в консоли.
- Коды выхода: `0` при успехе (в том числе частичном по ресурсам), `1` при ошибке главной страницы, `2` при ошибке файловой системы.
- `node bin/page-loader.mjs --help` или без аргументов — понятное сообщение, а не сырой стектрейс.
- `node --test` проходит, в нём минимум четыре теста без обращения к реальной сети и реальному диску.
