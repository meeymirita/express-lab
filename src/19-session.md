# Сессия 19 · Финал части II: ShareBox Teams
dur: ~5 ч

## 19.1 Задание: командные пространства | short: Итоговое задание части II | est: ~5 ч
### intro
**Слова шага:** *техническое задание (ТЗ)*, *приёмка*, *самопроверка*.

Новой теории в этой сессии нет: ты собираешь объёмное расширение ShareBox по описанию, используя весь курс — обе части. Готового решения здесь нет, и так задумано: опирайся на свой код из сессий 1–18 и на справочные разделы методички.

**Задача.** ShareBox используют не только одиночки — команде нужно общее пространство: одна папка со share-ссылками, видимая всем участникам, с ролями и журналом того, кто что сделал.

**Запуск:**
```text
docker compose up --build --scale app=2
```
(два экземпляра Express за Caddy — убедись, что ничего не ломается от того, что запрос может попасть на любой из двух).

**1. Данные.** Новые таблицы (Prisma-схема, своя миграция):
```text
teams          (id, name, created_at)
team_members   (id, team_id → teams.id, user_id → users.id, role, created_at) — role: owner | admin | member
team_shares    (id, team_id → teams.id, share_id → shares.id, added_by → users.id, created_at)
audit_log      (id, team_id → teams.id, actor_id → users.id, action, target, at)
import_jobs    (id, team_id → teams.id, status, total, done, failed, created_at)
```
`shares` (сессия 16) не меняется — команда лишь **видит** существующую ссылку через `team_shares`, владелец ссылки остаётся тем же пользователем.

**2. Роли команды.** `owner` (создатель, один на команду, не может выйти, пока не передаст роль) → `admin` (приглашает/исключает `member`, не может исключить `owner`) → `member` (видит общие ссылки, может добавлять свои ссылки в команду, не может исключать других). Роль команды — отдельная сущность от `user.role` (`user`/`admin`) из сессии 17: администратор ShareBox в целом и администратор одной команды — разные права.

**3. API.**
| Метод | Путь | Кто |
|---|---|---|
| `POST` | `/v1/teams` | любой вошедший — создаёт команду, становится `owner` |
| `POST` | `/v1/teams/:id/members` | `owner`/`admin` — приглашает участника по email, по умолчанию `member` |
| `DELETE` | `/v1/teams/:id/members/:userId` | `owner`/`admin`, нельзя исключить `owner` |
| `PATCH` | `/v1/teams/:id/members/:userId` | `owner` — меняет роль участника |
| `POST` | `/v1/teams/:id/shares` | участник команды — добавляет свою существующую ссылку в общую папку |
| `GET` | `/v1/teams/:id/shares` | участник команды — список общих ссылок с именем добавившего |
| `GET` | `/v1/teams/:id/audit` | `owner`/`admin` — журнал событий команды |

Идемпотентный ключ (сессия 10.2) — обязателен для `POST /v1/teams/:id/members` (повторное приглашение по сети не должно продублировать запись).

**4. Пакетный импорт.** `POST /v1/teams/:id/imports` с CSV-файлом (`shareCode,note` построчно) ставит задачу в **свою** очередь (в памяти процесса или в базе — не Redis, см. решение владельца 14.10), сразу отвечает `202 Accepted` с `importJobId`; `GET /v1/imports/:id` отдаёт `{ status, total, done, failed }`, обновляется по мере обработки. Обработка — не более 3 ссылок одновременно (пул, как `--limit` в финале части I).

**5. Журнал (audit log).** Каждое изменение команды (создание, приглашение, исключение, смена роли, добавление ссылки) пишет строку в `audit_log`: `actor_id` (кто), `action` (код события), `target` (на что подействовало), `at`. `GET /v1/teams/:id/audit` отдаёт последние 50 записей с именами вместо голых `id`.

**6. Webhook по факту скачивания.** Команда может задать один URL (`teams.webhook_url`, добавь поле миграцией); при каждом скачивании общей ссылки (`team_shares`) ShareBox отправляет `POST` на этот URL с телом `{ teamId, shareCode, at }`. Сетевая ошибка отправки (webhook недоступен) **не должна** мешать самому скачиванию — отправка асинхронная, с одной повторной попыткой через секунду, ошибка только логируется.

**7. OpenAPI.** Расширь `openapi.yaml` (сессия 10.5) до всех путей таблицы из п. 3 — не только двух ресурсов из примера сессии 10.

**8. Множественные инстансы.** Прогони `docker compose up --scale app=2` — ничего не должно зависеть от памяти конкретного процесса (счётчик скачиваний, очередь импорта — через базу, не через `Map` в памяти одного инстанса: два инстанса должны видеть одну и ту же задачу импорта и один и тот же журнал).

**9. Тесты.** Минимум шесть тестов на `node:test`: роль `member` не может пригласить участника (403); повторный идемпотентный `POST /members` с тем же ключом не создаёт вторую запись; `owner` нельзя исключить; импорт с одним битым `shareCode` в CSV всё равно обрабатывает остальные и помечает `failed: 1`; webhook-ошибка не прерывает скачивание (замокай сетевой вызов); два параллельных `POST /teams/:id/members` с одним email не создают двух участников.

**Чего не требуется:** фронтенда, email-уведомлений о приглашении (только запись в базу), более двух уровней вложенности прав, UI для журнала — только API.

**Порядок работы (подсказка, не решение):** сначала данные и роли без импорта/webhook/аудита — команда, участники, видимость ссылок; затем аудит (он понадобится для отладки остального); затем импорт с очередью; затем webhook; затем идемпотентность и тесты на конкурентность; в конце — OpenAPI и прогон с двумя инстансами.

### why
Здесь соединяется весь курс: REST и идемпотентность (сессия 10), роли и авторизация (сессия 14, 17), транзакции и конкурентные данные (сессия 12, 13), очередь с ограничением параллельности (та же идея, что `worker_threads`/пул в сессии 4 и финале части I, но для сетевых и фоновых задач), наблюдаемость через журнал (сессия 17), устойчивость к частичным сбоям (сессия 15 — устойчивость загрузки, здесь — устойчивость импорта и webhook), тесты на моках (сессия 6) и, наконец, работа без состояния в памяти процесса — то, без чего `--scale app=2` сразу же покажет нестабильное поведение.

### quiz
- Проверь себя: выполнено ли задание?
- Роль команды (`owner`/`admin`/`member`) отделена от `user.role` ShareBox и проверяется отдельным middleware.
- `owner` нельзя исключить и нельзя оставить команду без владельца.
- Повторный `POST /v1/teams/:id/members` с тем же идемпотентным ключом не создаёт вторую запись (проверено тестом).
- Импорт ставится в очередь, отвечает `202` сразу, не более 3 ссылок обрабатываются одновременно, частичный сбой не останавливает остальные.
- Журнал команды показывает последние события с именами, а не только `id`.
- Ошибка отправки webhook не мешает самому скачиванию и не теряется молча (залогирована).
- `openapi.yaml` описывает все пути из таблицы задания, а не только часть.
- `docker compose up --scale app=2` работает: счётчики и статусы импорта одинаковы независимо от того, какой инстанс обработал запрос.
- `node --test` проходит, в нём минимум шесть новых тестов, включая конкурентный сценарий.
