## 2.1 Event loop на примерах | short: Event loop | est: ~20 мин
### intro
**Слова шага:** *event loop* — порядок, в котором Node выполняет синхронный код, потом отложенные задачи; *стек вызовов (call stack)* — что выполняется прямо сейчас; *очередь задач* — что ждёт своей очереди после синхронного кода; `setTimeout` — отложить выполнение колбэка на N миллисекунд.

Node — однопоточный: весь твой JS-код выполняется в одном потоке. Чтобы при этом не зависать на медленных операциях (чтение файла, сеть), Node использует **event loop**: сначала выполняется весь синхронный код до конца (**стек вызовов** пустеет), и только потом — то, что отложено (таймеры, завершённые операции ввода-вывода). Увидим это на `setTimeout(..., 0)` — ноль миллисекунд не значит «сейчас же»:

**Файл:** `event-loop-demo.js`.

```bash run
cd /work/sharebox
cat > event-loop-demo.js <<'EOF'
console.log('1: синхронный код сверху')
setTimeout(() => console.log('3: из очереди (даже с 0 мс)'), 0)
console.log('2: синхронный код снизу')
EOF
node event-loop-demo.js
```

### result
```out auto
```

### why
Это объясняет самую частую растерянность новичка: «почему код выше выполнился позже кода ниже?». Любой колбэк — таймера, сети, файла — всегда ждёт, пока синхронный код полностью закончится, сколько бы ты ни ставил `0` в `setTimeout`. Эта модель — основа для Express: пока один запрос ждёт базу, Node успевает обслуживать другие.

### deep Под капотом
Полная модель event loop в Node — несколько фаз (timers, pending callbacks, poll, check, close) поверх библиотеки libuv; в этой лабе хватает упрощённой версии «сначала весь синхронный код, потом очередь» — для работы с Express этого достаточно.

### deep Если не получилось
- **Порядок другой, чем ожидала** — убедись, что в файле ровно три `console.log`/`setTimeout`, как в примере; скопированный код с опечаткой в порядке строк даст другой, но тоже объяснимый результат.

- Изменится ли порядок, если поставить `1000` вместо `0`? Почему для порядка это не важно?
- Что должно быть пустым (стек вызовов), прежде чем event loop возьмёт следующую задачу из очереди?

## 2.2 Callbacks и колбэк-ад | short: Callbacks | est: ~25 мин
### intro
**Слова шага:** *callback* — функция, которую вызовут позже с результатом; *error-first callback* — колбэк, где первый аргумент — ошибка или `null`; *callback hell* — вложенные друг в друга колбэки, которые трудно читать.

До промисов асинхронный результат получали через **callback** — функцию, которую передают и которую вызовут позже, когда результат готов. В Node это почти всегда **error-first**: первым аргументом — ошибка или `null`, вторым — результат.

**Файлы:** `readme-callback.txt`, `callback-demo.js`.

```bash run
cat > readme-callback.txt <<'EOF'
строка 1
строка 2
EOF
cat > callback-demo.js <<'EOF'
import { readFile } from 'node:fs'

readFile('readme-callback.txt', 'utf8', (err, data) => {
  if (err) {
    console.error('ошибка:', err.message)
    return
  }
  console.log('прочитано:', data.split('\n').length - 1, 'строк(и)')
})
console.log('эта строка печатается раньше чтения файла')
EOF
node callback-demo.js
```

Теперь дадим каждому чтению зависеть от предыдущего — классический **callback hell**: колбэк внутри колбэка, лесенка вправо.

**Файл:** `callback-hell-demo.js`.

```bash run
cat > callback-hell-demo.js <<'EOF'
import { readFile } from 'node:fs'

readFile('readme-callback.txt', 'utf8', (err, a) => {
  if (err) return console.error(err.message)
  readFile('package.json', 'utf8', (err, b) => {
    if (err) return console.error(err.message)
    console.log('первый файл:', a.length, 'символов')
    console.log('второй файл:', b.length, 'символов')
  })
})
EOF
node callback-hell-demo.js
```

### result
```out auto
```

### why
`if (err) return ...` в начале каждого колбэка — обязательный ритуал: забыл проверить `err` — программа продолжит с `data === undefined` и упадёт на следующей строке с непонятной ошибкой. А лесенка из двух вложенных чтений — это ещё читаемо; на пяти шагах (прочитать → проверить → записать → уведомить → залогировать) код превращается в нечитаемый треугольник. Это и есть причина, по которой появились промисы.

### deep Если не получилось
- **`console.log('эта строка...')` печатается раньше результата чтения** — так и задумано: `readFile` асинхронный, колбэк выполнится позже, когда файл реально прочитан (сверь с шагом 2.1).
- **`ENOENT: no such file or directory`** — файл `readme-callback.txt` не создан в этой же сессии; выполни блок заново сверху.

## 2.3 Promise | short: Promise | est: ~25 мин
### intro
**Слова шага:** `Promise` — объект-обещание результата, который будет позже; `.then` — что делать, когда промис выполнился; `.catch` — что делать при ошибке; `Promise.all` — дождаться сразу нескольких промисов; `fs/promises` — версия модуля `fs`, где функции возвращают промисы.

**Promise** — объект-обещание: «результат будет, но позже» в одном из трёх состояний (ожидание, выполнено, отклонено). У модуля `fs` есть promise-версия — `node:fs/promises` — те же функции, но возвращают `Promise` вместо приёма колбэка. Перепишем шаг 2.2 без вложенности:

**Файл:** `promise-demo.js`.

```bash run
cat > promise-demo.js <<'EOF'
import { readFile } from 'node:fs/promises'

readFile('readme-callback.txt', 'utf8')
  .then((a) => {
    console.log('первый файл:', a.length, 'символов')
    return readFile('package.json', 'utf8')
  })
  .then((b) => console.log('второй файл:', b.length, 'символов'))
  .catch((err) => console.error('ошибка:', err.message))

Promise.all([
  readFile('readme-callback.txt', 'utf8'),
  readFile('package.json', 'utf8'),
]).then(([a, b]) => console.log('Promise.all — оба сразу:', a.length, b.length))
EOF
node promise-demo.js
```

**Разбор.** Каждый `.then` получает результат предыдущего и может вернуть новый `Promise` — следующий `.then` в цепочке дождётся и его. Один `.catch` в конце ловит ошибку из **любого** звена цепочки — не нужно проверять `err` после каждого шага. `Promise.all([...])` — запускает несколько промисов **параллельно** и ждёт, пока выполнятся все; порядок результатов в массиве совпадает с порядком в `Promise.all`, а не с тем, какой файл прочитался быстрее.

### result
```out auto
```

### why
Промисы решают лесенку из 2.2: вложенность превращается в цепочку `.then`, а обработка ошибок — в один `.catch` вместо `if (err)` на каждом шаге. `Promise.all` — то, как в ShareBox дальше будут одновременно проверяться, например, права на файл и его существование, без ожидания по очереди.

### deep Если не получилось
- **`UnhandledPromiseRejection`** — где-то в цепочке `Promise` отклонился, а `.catch` не стоит в конце или стоит не у той цепочки; каждая независимая цепочка промисов нуждается в своём `.catch` (или общем `try/catch` с `async/await` — следующий шаг).
- **Порядок строк между `.then`-цепочкой и `Promise.all`** может отличаться от примера — оба куска кода стартуют почти одновременно и выполняются независимо; это нормально и ожидаемо для асинхронного кода.

## 2.4 async/await | short: async/await | est: ~20 мин
### intro
**Слова шага:** `async` — помечает функцию, которая всегда возвращает промис; `await` — дождаться результата промиса внутри `async`-функции; `try`/`catch` с промисами — ловит отклонённый промис так же, как обычное исключение.

`async`/`await` — синтаксический сахар над промисами: код выглядит как синхронный (сверху вниз), а на самом деле каждая строка с `await` ждёт выполнения промиса, не блокируя остальной Node. Перепишем шаг 2.3:

**Файл:** `async-demo.js`.

```bash run
cat > async-demo.js <<'EOF'
import { readFile } from 'node:fs/promises'

async function main() {
  try {
    const a = await readFile('readme-callback.txt', 'utf8')
    const b = await readFile('package.json', 'utf8')
    console.log('первый:', a.length, 'символов, второй:', b.length, 'символов')
  } catch (err) {
    console.error('ошибка:', err.message)
  }
}

main()
EOF
node async-demo.js
```

**Разбор.** `async function` — функция, которая всегда возвращает `Promise`, даже если внутри нет явного `return`. `await` можно писать только внутри `async`-функции (или на верхнем уровне ESM-модуля — *top-level await*, пригодится при подключении к базе в сессии 5). `try`/`catch` вокруг `await` ловит отклонённый промис точно так же, как обычное исключение.

### result
```out auto
```

### why
Из трёх способов (колбэки → промисы → `async`/`await`) весь дальнейший код ShareBox, включая Express-роуты, написан на `async`/`await` — он читается как обычный последовательный код, и именно так выглядит реальный промышленный Node-код сегодня.

### deep Если не получилось
- **`await is only valid in async functions`** — `await` написан вне `async function` и не на верхнем уровне ESM-модуля; оберни в `async function` или проверь, что `package.json` задаёт `"type": "module"` (шаг 1.4) для top-level await.
- **Ошибка «проглочена»** — `catch` поймал её, но ничего не вывел; не забывай `console.error` или `throw` дальше, если ошибку нужно показать.

## 2.5 EventEmitter | short: EventEmitter | est: ~20 мин
### intro
**Слова шага:** `EventEmitter` — объект, который умеет испускать именованные события; `on` — подписаться на событие; `emit` — вызвать событие, оповестив подписчиков; *подписчик (listener)* — функция, которая сработает при событии.

Промисы и `async`/`await` годятся для «результат один раз». Но что, если событий много и заранее неизвестно сколько (клики, новые данные из сети)? Для этого в Node — **`EventEmitter`**: объект, на котором можно подписаться (`on`) на именованное событие, и позже кто угодно может его вызвать (`emit`) — сработают все подписчики по очереди.

**Файл:** `events-demo.js`.

```bash run
cat > events-demo.js <<'EOF'
import { EventEmitter } from 'node:events'

const uploads = new EventEmitter()

uploads.on('done', (name) => console.log('загрузка завершена:', name))
uploads.on('done', (name) => console.log('→ отправить письмо про', name))

uploads.emit('done', 'photo.png')
uploads.emit('done', 'report.pdf')
EOF
node events-demo.js
```

### result
```out auto
```

### why
`EventEmitter` — это не экзотика, а фундамент: `req`/`res` в `node:http` (шаг 1.6) — тоже `EventEmitter` (события `'data'`, `'end'`, `'error'`), и потоки (следующий шаг) построены на нём же. Понимание `on`/`emit` объясняет, почему у объектов вроде `req` можно писать `req.on('data', ...)`.

### deep Под капотом
`emit` вызывает подписчиков **синхронно** и **по порядку подписки** — в примере выше сначала «загрузка завершена», потом «отправить письмо», для каждого файла. Если подписчиков нет, `emit` просто ничего не делает (кроме особого события `'error'` — без подписчика на него Node уронит процесс).

### deep Если не получилось
- **Обработчик не сработал** — проверь точное совпадение имени события (`'done'` ≠ `'Done'`, регистр важен) и что `on` стоит в коде раньше `emit`.
- **`Unhandled 'error' event'`** — особый случай: если возникло событие `'error'` без своего `on('error', ...)`, Node считает это необработанным исключением и завершает процесс.

## 2.6 Buffer и потоки: копируем файл | short: Streams и Buffer | est: ~30 мин
### intro
**Слова шага:** `Buffer` — кусок памяти с сырыми байтами; *поток (stream)* — чтение/запись данных по частям, не всё сразу; `Readable` — поток, из которого читают; `Writable` — поток, в который пишут; `pipe` — соединить читающий поток с пишущим; *обратное давление (backpressure)* — автоматическое торможение чтения, если запись не успевает.

Строки в JS — это текст в определённой кодировке. Но файлы, сеть, картинки — это **байты**, и для них в Node есть `Buffer` — кусок памяти с сырыми байтами:

```bash run
node -e "console.log(Buffer.from('ok', 'utf8'))"
```

Для больших файлов читать их целиком в память (как `readFile` до сих пор) — плохая идея: файл 200 МБ (лимит ShareBox, сессия 8) съест 200 МБ оперативной памяти разом. **Поток (stream)** читает и пишет **кусками (chunks)**, не дожидаясь, пока весь файл будет готов. Скопируем файл потоком:

**Файл:** `copy-stream.js`.

```bash run
head -c 200000 /dev/urandom > big.bin
cat > copy-stream.js <<'EOF'
import { createReadStream, createWriteStream } from 'node:fs'

const src = createReadStream('big.bin')
const dst = createWriteStream('big-copy.bin')

let chunks = 0
src.on('data', (chunk) => { chunks += 1 })
src.pipe(dst)
dst.on('finish', () => console.log('скопировано чанков:', chunks))
EOF
node copy-stream.js
```

Проверим, что копия точно того же размера:

```bash run
wc -c big.bin big-copy.bin
```

**Разбор.** `createReadStream`/`createWriteStream` — читающий и пишущий поток, оба `EventEmitter` (шаг 2.5): событие `'data'` на каждый кусок, `'finish'` — когда запись закончена. `.pipe(dst)` — соединяет читающий поток с пишущим и сам управляет скоростью (**backpressure**): если `dst` пишет на диск медленнее, чем `src` читает, `pipe` сам притормозит чтение, чтобы память не росла бесконтрольно.

### result
```out auto
```

### why
Это ровно то, что в сессии 8 позволит принимать файлы до 200 МБ без роста памяти процесса: `multer` и скачивание с `Range` построены на тех же `Readable`/`Writable` и том же `pipe`. Без понимания потоков непонятно, почему «просто прочитать файл в память» для ShareBox — неправильный путь.

### deep Если не получилось
- **Размеры `big.bin` и `big-copy.bin` разные** — копирование не завершилось до `wc -c`; в реальном коде (не в тестовом скрипте) жди событие `'finish'`, прежде чем считать файл готовым — как и сделано в примере через `console.log` внутри `'finish'`.
- **Процесс «висит»** — обычно значит, что `'finish'` не наступил (поток не закрылся); проверь, что `.pipe()` вызван, а не только `.on('data', ...)` — без `.pipe()` или ручной записи данные читаются, но никуда не пишутся.
